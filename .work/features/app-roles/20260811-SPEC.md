# Client-App Roles (appsuper / appglobal) — Feature SPEC

**Status:** Approved
**Approved:** 2026-08-11 (owner, via @x-director; Q1 unconditional appglobal, Q2 no roles at code-exchange, Q3 appsuper may target inaccessible app — assumptions confirmed)
**Owner:** owner (product) + eng
**ADRs referenced:** none
**Related plans:** tactical backlog `.work/plans/NEXT.md` (no approved master plan — out-of-plan SPEC, owner-directed)

## 1. Purpose

Original request (verbatim): *"need to define any registered user of any app as super-user (or administrator)"* — refined by owner (2026-08-11) into a **role system for client applications** with exactly two roles, named to avoid any ambiguity with platform roles:

- **`appsuper`** — granted to a user **within one specific application** (per-app role).
- **`appglobal`** — granted to a user **without any specific application** (all-apps role; one standing row, no bulk fan-out, covers present and future apps).

Ground rules set by the owner:

- tools-dashboard **stores, manages, and reports** these role assignments — and that is all. Assignments confer **no privileges inside tools-dashboard itself** (holders are *not* Administrators).
- tools-dashboard **provides client apps a way to query these roles**; **what each role means (what extra functionality it unlocks) is defined and enforced entirely by the client app** (e.g. E-Cards).
- The model is **role-generic** so additional client-app roles can be added later **without schema reshape**.

This never touches the platform-global role model (`users.role` stays `admin`/`customer`/`moderator`/`support`, `back-auth/core/database.py:46`) — `appsuper`/`appglobal` are a separate axis, visible only to client apps.

## 2. In scope / Out of scope

**In scope**

- New persisted assignment: `(user, role, app_id?)` in PostgreSQL — `appsuper` rows carry an `app_id`; `appglobal` rows have `app_id NULL`. v1 roles: exactly `{"appsuper", "appglobal"}`.
- Grant/revoke/list APIs + admin UI, operable by **platform admins only**, from **both** directions: the app detail page (who holds `appsuper` on this app) and the user detail page (what this user holds, incl. `appglobal`).
- **Client-app query channel**: an OAuth client app can learn a user's app-role list *for its own app* — via access-token claim (fast path) and via `validate-token` (authoritative, real-time). An `appglobal` holder verifies with `appglobal` on every app (R15).
- **Self-applying schema**: the new table is created/verified idempotently at service startup by *both* schema channels (migration runner + back-auth `create_all`) — a plain `docker compose up` / restart converges the database with zero manual steps (see §5).
- Audit events for grant/revoke (role + scope recorded in the event payload).
- en/es locale strings for all new UI.

**Out of scope (explicit)**

- **Any tools-dashboard privilege for role holders.** `appsuper`/`appglobal` holders are **not** Administrators: no admin-console sign-in, no ability to view or modify app registrations, access rules, permissions, status, secrets, or any other data in tools-dashboard. All console surfaces remain platform-admin-only, exactly as today. This holds for any future client-app role too, unless a future SPEC explicitly says otherwise.
- Changes to the platform-global role model (`admin`/`customer`/`moderator`/`support`, `DEFAULT_ROLE_PERMISSIONS`) — untouched.
- Changes to how app *access* itself is computed (access rules, subscription tiers) — this feature never modifies `app_access_rules`.
- Defining or enforcing what `appsuper`/`appglobal` *mean* inside any client app — the client app owns role semantics, including any implication between them (e.g. whether `appglobal` should imply `appsuper` powers inside the app is the app's decision, R12).
- **Defining additional roles** (beyond the two) — the model, APIs, and token contract accept them, but adding a new role name is a later, deliberate change (R6).
- **Bulk grant/revoke operations** — superseded by the `appglobal` role (single row, single revoke).
- Per-user grant rosters exposed to client apps (apps get a per-token role list for their own app, never a cross-app map).
- Cassandra canonical-profile sync (known pre-existing UUID/integer mismatch — see HANDOFF 2026-07-28).
- Self-service "request a role" flows.

## 3. Domain language

| Term | Meaning |
|------|---------|
| **Platform admin** | User with global `users.role = 'admin'`. Unchanged. The only actor that can grant/revoke client-app roles. |
| **Client-app role** | A string from the platform registry (`APP_ROLES`) assignable to a user. Meaningless inside tools-dashboard — carries no console privilege. Its meaning is defined by the client app. |
| **`appsuper`** | Per-app role: row **must** have `app_id` set. "User U is appsuper of app X." |
| **`appglobal`** | All-apps role: row **must** have `app_id NULL`. "User U is appglobal" — verifies on every app, present and future. |
| **Scope pairing** | The enforced 1:1 binding between role and scope: `appsuper` ⇔ app required, `appglobal` ⇔ no app. Violations are rejected (422 API / DB CHECK). |
| **App / client** | An `oauth_clients` row (`id` UUID, `client_id` string) surfaced in the app library. OAuth tokens carry `aud = client_id`. |
| **Grant / revoke** | Platform-admin actions creating/deleting an `app_user_roles` row. |
| **Query channel** | How a client app learns the role list: JWT claim `app_roles` (fast, possibly stale ≤ access-token TTL) or `POST /auto-auth/validate-token` response field `app_roles` (authoritative, real-time). |

Naming decision (owner, 2026-08-11): roles are named **`appsuper`** and **`appglobal`** in code, APIs, tokens, and UI — never "superuser"/"administrator". `admin` remains the platform-global role name, and a client-app role holder is explicitly **not** an Administrator.

## 4. Behavioural spec

**Grant / revoke (tools-dashboard, platform admins only)**

- R1. Only a platform admin (`require_admin`) can grant, revoke, or list client-app role assignments. No self-grant path exists.
- R2. An `appsuper` grant target must be an existing registered user (any `users` row, any global role) and an existing non-deleted app. An `appglobal` grant target is an existing user only (no app — enforced by scope pairing, R6.1). Duplicate grant of an existing `(app_id|NULL, user_id, role)` row is idempotent (200/204, no error, no duplicate row). A user **may hold both roles** (e.g. `appglobal` plus a per-app `appsuper` row — they are independent rows; see R15.4).
- R3. Revoke is per `(app_id|NULL, user_id, role)` and idempotent: revoking a non-existent assignment succeeds silently.
- R4. Grant and revoke write `app_audit_log` events (`app_role_granted` / `app_role_revoked`) with `performed_by` = acting platform admin; the `changes` payload records `{role, app_id?}`. `appglobal` events use `app_id NULL` on the audit row.
- R5. Deleting an app cascades-removes its `appsuper` assignments; deleting a user cascades-removes all their assignments, both roles (DB `ON DELETE CASCADE`).
- R6. **Role registry / extensibility:** valid roles and their scope pairing are defined in exactly two mirrored places — the DB CHECK constraints on `app_user_roles` and the `APP_ROLES` constant in back-api code (`{"appsuper": "per_app", "appglobal": "all_apps"}`).
  - R6.1 **Scope pairing is enforced twice**: API validation (422 on mismatch) and a DB CHECK (`(role='appsuper' AND app_id IS NOT NULL) OR (role='appglobal' AND app_id IS NULL)`).
  - R6.2 Adding a role later = one idempotent migration extending the CHECKs + one constant entry + UI copy; **no table reshape, no API version change, no token-contract change** (the contract already carries a list). The new role's scope pairing is declared in the same change.

**What a role holder is NOT (tools-dashboard side)**

- R7. A client-app role assignment (either role) confers **zero** privileges inside tools-dashboard:
  - R7.1 No admin-console access: front-admin loaders/endpoints keep `get_current_admin` / `require_admin` exactly as today; a user whose only distinction is a client-app role gets the same 403/redirect as any other non-admin.
  - R7.2 Cannot view or modify app registrations (name, URLs, redirect URIs, logo), access rules, subscription tiers, active status, or client secrets — those remain platform-admin-only.
  - R7.3 Cannot grant/revoke client-app roles for any app, including their own.
  - R7.4 Cannot view audit logs, usage stats, or user lists in tools-dashboard.
- R8. The role **applies to and is used by the client application**. tools-dashboard stores the assignment and reports the role list; the client application defines what actions each role allows inside itself and enforces them. tools-dashboard never models, validates, or interprets client-app permissions.

**Client-app query channel (e.g. E-Cards)**

- R9. **Authoritative, real-time:** `POST /auto-auth/validate-token` (back-auth) response gains `app_roles: string[]` — the roles the token's `sub` user holds that apply to the token's `aud` app: `appsuper` if a per-app row exists for that app, `appglobal` if an all-apps row exists (R15). v1 possible values: `[]`, `["appsuper"]`, `["appglobal"]`, `["appsuper", "appglobal"]`. Computed by DB lookup at call time; revocation is visible immediately.
- R10. **Fast path:** access tokens issued by `POST /auto-auth/issue-tokens` and `POST /auto-auth/refresh-tokens` include an `app_roles: string[]` claim for the token's `aud` client, computed at issuance with the same rule as R9. Apps validating JWTs locally via JWKS get the list with no extra call. Staleness: up to the access-token TTL (1h) after a grant/revoke; security-sensitive decisions must use R9.
- R11. **No cross-app leakage:** a token only ever carries/returns roles applying to its *own* audience app. There is no endpoint where app A can probe a user's roles on app B. `validate-token` reveals only the token-holder's own roles for the token's own audience — no new information beyond what the holder legitimately presents.
- R12. The contract is a **verbatim list of held role strings** applying to one app. It never enumerates assignments on other apps; the platform expresses **no implication between roles** (an `appglobal` holder gets `["appglobal"]`, not `["appsuper", "appglobal"]`, unless they also hold a per-app row — any "global implies super" logic is the client app's own decision, R8); clients treat unknown role strings as no-op (forward-compatible with future roles).

**Listing, scopes, and the appglobal role**

- R13. **User-centric listing:** a platform admin can list all role assignments of a user — `appsuper` rows (app id, client_id, app name, granted_by, created_at) and the `appglobal` row (marked, no app) — powering the user detail page.
- R14. **Two write paths, one repository operation:** `appsuper` grant/revoke (`PUT/DELETE /app-library/{app_id}/roles/{user_id}/appsuper`) and `appglobal` grant/revoke (`PUT/DELETE /users/{user_id}/app-roles/appglobal`) both delegate to the same repository write operation with `app_id` set or NULL — no divergent logic.
- R15. **appglobal semantics:** an `appglobal` row makes the user verify with `appglobal` in `app_roles` on **every app, present and future**, at query time (R9/R10).
  - R15.1 No per-app rows are created when `appglobal` is granted (no fan-out writes); revoking the single row removes the role everywhere in one delete.
  - R15.2 `appglobal` applies **unconditionally** — it is not re-filtered by access rules at query time (rationale and trade-off: §13 Q1). Portal visibility/launch is still gated by `app_access_rules` as today; this feature never changes who can *see or launch* an app.
  - R15.3 New apps registered later are covered automatically.
  - R15.4 An `appsuper` row and the `appglobal` row can coexist; effective `app_roles` are the union (deduplicated). Revoking one does not affect the other.
- R16. **App-centric listing shows effective holders:** the app detail page lists `appsuper` assignees of the app plus all `appglobal` holders (marked "appglobal — all apps"), so the admin sees everyone whose tokens will report a role for that app.
- R17. **UI copy uses the role names and states scope** at grant time ("Grant **appsuper** — this app…" with an app picker; "Grant **appglobal** — all apps, present and future" with no app picker, plus a note that revoke is a single action). The `appglobal` grant control exists **only** on the user detail page (it has no app context); the app detail page grants `appsuper` only.

**Schema application (idempotent, transparent, seamless)**

- R18. The `app_user_roles` table and the `app_audit_log` CHECK-constraint extension are applied **automatically on service start**, through two independent idempotent channels:
  - R18.1 `back-postgres/main.py` replays `back-postgres/schema/014_app_user_roles.sql` (all statements `IF NOT EXISTS` / idempotent guards) on every start, before HTTP traffic — the canonical schema path per `.cursorrules` migration policy.
  - R18.2 back-auth registers a mirror `Table("app_user_roles", ...)` in its SQLAlchemy metadata, so its existing startup `metadata.create_all` (checkfirst, with retry loop — `back-auth/core/database.py:104`) creates the table if the migration runner hasn't yet (fresh volumes, startup ordering races).
- R19. Both channels are safe to run N times and in any order: every statement is idempotent, and both definitions are byte-identical in shape (columns, types, constraints, indexes). The SQL script is the canonical definition; the back-auth metadata entry mirrors it (same rule as the `users` table, whose canonical home is `back-auth/core/database.py`).
- R20. Runtime fail-closed: if the table is somehow absent when a role lookup runs, the result is "no roles" (`app_roles: []`) plus a warning log — never an exception that breaks auth for everyone. A service restart then self-heals via R18.

## 5. Data model

New table, applied by **two idempotent startup channels** (R18/R19) — no manual step, no deploy ordering requirement:

**Channel 1 — canonical:** migration `back-postgres/schema/014_app_user_roles.sql` (via `@db-migration`), replayed by `back-postgres/main.py` on every service start before HTTP traffic:

```sql
CREATE TABLE IF NOT EXISTS app_user_roles (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    app_id UUID REFERENCES oauth_clients(id) ON DELETE CASCADE,  -- NULL = appglobal (all-apps)
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role VARCHAR(50) NOT NULL,
    granted_by INTEGER REFERENCES users(id),
    created_at TIMESTAMPTZ DEFAULT NOW(),
    CONSTRAINT valid_app_role CHECK (role IN ('appsuper', 'appglobal')),  -- extend via later migration (R6.2)
    CONSTRAINT valid_role_scope CHECK (                                   -- scope pairing (R6.1)
        (role = 'appsuper'  AND app_id IS NOT NULL) OR
        (role = 'appglobal' AND app_id IS NULL)
    )
);
-- Uniqueness per role (partial indexes are NULL-safe on all supported PG versions):
CREATE UNIQUE INDEX IF NOT EXISTS uq_app_user_roles_appsuper
    ON app_user_roles(app_id, user_id, role) WHERE app_id IS NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS uq_app_user_roles_appglobal
    ON app_user_roles(user_id, role) WHERE app_id IS NULL;
CREATE INDEX IF NOT EXISTS idx_app_user_roles_user ON app_user_roles(user_id);
CREATE INDEX IF NOT EXISTS idx_app_user_roles_app ON app_user_roles(app_id);
```

The script also extends the `app_audit_log.event_type` CHECK constraint with `app_role_granted`, `app_role_revoked` (drop-and-recreate guarded by a catalog check, so re-runs are no-ops). `app_audit_log.app_id` is already nullable (`007_app_library_tables.sql:119`), so `appglobal` audit events fit without change.

**Channel 2 — self-healing mirror:** back-auth adds `Table("app_user_roles", ...)` to the SQLAlchemy metadata in `back-auth/core/database.py`, byte-identical in shape to the script above. Its existing startup `metadata.create_all` (checkfirst + 10-attempt retry loop) then guarantees the table exists before back-auth serves tokens, even on a fresh volume or if back-auth starts before the migration runner. (Partial unique indexes are created by channel 1 only; SQLAlchemy `create_all` covers the table + plain indexes, and the mirror is a startup safety net, not the canonical DDL.)

No changes to `users`, `oauth_clients`, or `app_access_rules`. back-auth reads `app_user_roles` from the same PostgreSQL it already owns (users table) — no new service hop.

**Why this shape (extensibility):** role as a column (not a per-role table, not boolean columns) means a new role is a CHECK-extension migration + constant entry, not new tables; scope pairing lives in one CHECK + one registry constant (R6.1); uniqueness via partial unique indexes keeps both roles collision-free; the token/API contract carries `string[]`, so clients and tokens need no contract change when roles are added (R6.2, R12).

## 6. APIs

**back-api** — all platform-admin-only (`get_current_admin`, unchanged guard). Endpoints live on `admin_router` (`/api/admin`, `features/app-library/api.py`):

| Endpoint | Purpose |
|----------|---------|
| `GET /app-library/{app_id}/roles` | List **effective** holders for an app: `appsuper` assignees + `appglobal` holders, role marked (R16) — app detail page |
| `PUT /app-library/{app_id}/roles/{user_id}/{role}` | `appsuper` grant (idempotent; 422 if role unknown or scope-paired wrong — R6.1) |
| `DELETE /app-library/{app_id}/roles/{user_id}/{role}` | `appsuper` revoke (idempotent) |
| `GET /users/{user_id}/app-roles` | List a user's assignments, both roles (R13) — user detail page |
| `PUT /users/{user_id}/app-roles/{role}` | **`appglobal` grant** (idempotent; 422 if role unknown or scope-paired wrong) |
| `DELETE /users/{user_id}/app-roles/{role}` | `appglobal` revoke (idempotent) — one action removes the role everywhere (R15.1) |

Both grant families delegate to the same repository write (R14). Role-generic by construction (R6.2): the v1 UI only offers the two roles, but the endpoints accept any registered role without future modification.

No changes to any existing app-library or user-management endpoint: `create_app`, `update_app`, `delete_app`, `toggle_status`, `regenerate_secret`, `update_access_control`, `get_app_admin`, `get_usage_stats`, `list_all_apps`, `update_user_role`, etc. all keep their current guards untouched (R7).

**back-auth** (`features/auto-auth/api.py` + token service/domain):

| Surface | Change |
|---------|--------|
| `POST /auto-auth/validate-token` | Response `ValidateTokenResponse` gains `app_roles: list[str]` (R9) — `appsuper` if a per-app row exists for `(aud → oauth_clients.id, sub → user_id)`, plus `appglobal` if an all-apps row exists |
| `POST /auto-auth/issue-tokens` | Access-token payload gains `app_roles: list[str]` claim for `aud` (R10), same rule |
| `POST /auto-auth/refresh-tokens` | Same claim recomputed at refresh (fixes the placeholder user lookup at the same time — `user_email`/`user_name` TODO at api.py:310-313) |

**front-admin** (platform-admin console only — R7.1):

- **App detail page** (`admin.features.app-library.$appId.tsx`): new **"appsuper"** card beside the Access card — lists effective holders (`appsuper` assignees + `appglobal` holders, role marked, R16), grant `appsuper` (user picker reusing the existing debounced user search from the Access tab), revoke per row. `appglobal` rows shown here are revoked from the user detail page only (they are not app-scoped), with copy saying so.
- **User detail page** (`admin.features.user-management.$userId.tsx`): new **"Client-app roles"** card — lists everything the user holds (`appsuper` rows with app names + `appglobal` badge), per-row revoke, and two clearly separated grant controls (R17): **"Grant appsuper — this app…"** (app picker + grant) and **"Grant appglobal — all apps, present and future"** (single action, no app picker, explicit copy + confirm). 
- New proxy routes `admin.api.app-library.*` / `admin.api.users.*` mirroring the existing `admin.api.users.$userId.role.tsx` pattern; en/es locale strings for all of the above (role names `appsuper`/`appglobal` stay untranslated as product terms; surrounding copy translated).

## 7. Invariants

- I1. A client-app role assignment never widens the global `users.role` or `users.permissions`, and never changes any tools-dashboard authorization decision (R7).
- I2. Existing console authorization is byte-for-byte unchanged: everything requires exactly what it requires today.
- I3. At most one `appsuper` row per `(app_id, user_id)` and one `appglobal` row per `user_id` (partial unique indexes, §5).
- I4. Every grant/revoke leaves an audit row naming the role (and app, for `appsuper`).
- I5. A client app can only ever learn role assignments applying to **itself** (R11); the platform never exposes a user's cross-app role map to clients.
- I6. Role validity and scope pairing are enforced at two mirrored layers (DB CHECKs + code registry, R6/R6.1); they must never diverge — a migration adding a role updates both in the same change.
- I7. `appsuper` and `appglobal` writes share one repository operation (R14) — no divergent grant implementations.
- I8. An `appglobal` grant never creates per-app rows; the effective list is computed by union at read/query time (R15.1, R15.4).
- I9. The platform reports held roles verbatim — it never expands, implies, or derives one role from another (R12).

## 8. Error model

| Case | HTTP | Body |
|------|------|------|
| Unauthenticated (grant APIs) | 401 | existing auth error shape |
| Authenticated, not platform admin (grant APIs — **including role holders**) | 403 | existing admin-required shape |
| Grant target user/app not found | 404 | existing not-found shape |
| Role not in registry | 422 | `{"detail": "Invalid role: <role>. Must be one of: appglobal, appsuper"}` |
| Role/scope mismatch (`appglobal` with app, `appsuper` without app) | 422 | `{"detail": "Role <role> requires scope <per_app|all_apps>"}` (R6.1) |
| App soft-deleted (`appsuper` grant) | 404 | treat as not found |
| `validate-token` with unknown `aud` app | 200 | `valid: true, app_roles: []` (no existence oracle for apps) |
| Validation (bad ids) | 422 | FastAPI default |

Grant/revoke of an already-correct state is **not** an error (R2/R3). `validate-token` failure modes unchanged (invalid token → `valid: false`).

## 9. Observability

- Structured logs on grant/revoke (`app_role.grant` / `app_role.revoke`) with internal ids and role only (no emails — no-PII rule).
- Audit via `app_audit_log` (R4) — queryable per app by platform admins; `appglobal` events have `app_id NULL`.
- `validate-token` role lookups add one indexed Postgres read (union of per-app + all-apps rows); no new metrics for v1 (reuse existing request logging).

## 10. Security and privacy

- Privilege-escalation surface is the grant endpoints — platform-admin-only (R1) and audited (R4). A role holder cannot use the feature to touch tools-dashboard at all (R7).
- `appglobal` is the highest-blast-radius object in this feature — mitigated by: platform-admin-only, grant control isolated on the user detail page with explicit copy + confirm (R17), every grant/revoke audited (R4), and single-action revoke (R15.1).
- Client-side staleness is bounded and documented: the JWT claim (R10) can be stale ≤1h; apps must use `validate-token` (R9) for decisions that must reflect revocation immediately (e.g. gating elevated powers inside E-Cards).
- The query channel cannot be used as an app-existence or cross-app-assignment oracle (R11, §8 unknown-aud rule).
- The meaning of each role inside the client app is the client app's responsibility (R8) — tools-dashboard's security boundary ends at reporting assignments truthfully and verbatim (I9).
- No PII in logs; grant UIs show user emails to platform admins only (they already see them in user management).
- Threat-model note: compromise of a client app's token-validation path could forge role status *inside that app only*; tools-dashboard data and other apps are unaffected (R11/R12, I5).

## 12. Rollout and rollback

- Rollout: deploy `back-auth` + `back-api` + `front-admin` + restart the stack; schema applies itself on start (R18 — migration runner replays `014_*.sql`, back-auth `create_all` covers any startup race). **No manual SQL, no deploy ordering, no backfill** (feature starts with zero assignments). New response field/claim is additive — existing client apps ignore it safely.
- Verification after start: migration runner logs (`migration.run` result ok), `app_user_roles` present in `information_schema`, smoke `bash bin/test.sh`; manual browser pass over both grant UIs (app detail + user detail).
- Rollback: revert code deploys; table may stay (unused). Tokens already issued keep the claim until expiry — harmless (absence vs `[]` are equivalent for unaware apps).
- Client apps (E-Cards et al.) adopt the field on their own schedule; nothing breaks before they do.
- **Adding a role later** (post-v1): idempotent migration extending the CHECKs + `APP_ROLES` entry (with its scope pairing) + UI copy; no other change (R6.2, I6).

Alternative: evaluate `app_access_rules` per query call, which would duplicate that logic in back-auth or add a back-auth→back-api hop. | owner | unconditional — simpler, no new hop; access rules still gate portal visibility/launch as today |
| Q2 | Should `POST /auto-auth/validate-code` also return `app_roles` at code-exchange time, or is validate-token + claim enough? | owner | validate-token + claim is enough for v1 |
| Q3 | May an `appsuper` grant target an app the user **cannot** currently access? | owner | yes — admin's choice; role and access are independent axes |

Resolved 2026-08-11: client-app query channel **is** in scope (R9–R12); role holders have **no** tools-dashboard privileges and are not Administrators (R7); role semantics belong to the client app (R8); model must be role-generic for future roles (R6); grant UI on **both** app detail and user detail pages; **bulk grant/revoke replaced by the `appglobal` role** (R15); roles named **`appsuper`** (per-app) and **`appglobal`** (all-apps) with enforced scope pairing (R6.1).
